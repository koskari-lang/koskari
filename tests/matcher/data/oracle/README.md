# Matcher oracle corpus

Pattern specs, subjects and inline `match` arms, with the outcomes
master's native matcher engine gave them. `tests/matcher/oracle.py`
reads these files, runs every case on this tree and compares.

Two corpora, each a standalone and an inline file, generated by
`generate.py` (beside this file) under master 4d079fa3 (`run-master.sh`
after `build-master.sh`, master's own build environment), with the spec
builder, value codec and extern set of `tests/matcher/oracle.py`:

    MASTER_PATH=$PWD/tests/matcher \
        tests/matcher/data/oracle/run-master.sh tests/matcher/data/oracle/generate.py OUTDIR
    MASTER_PATH=$PWD/tests/matcher \
        tests/matcher/data/oracle/run-master.sh tests/matcher/data/oracle/generate.py OUTDIR --seed 77777

Rerunning each reproduces its two files byte for byte.

## Seeds and sizes

Each corpus uses one `random.Random` for both of its files.

| seed | files | standalone | inline |
|---|---|---|---|
| 20261017 | standalone.json, inline.json | 430 records, 3416 cases | 300 records, 1800 cases (9 renderings dropped) |
| 77777 | standalone-77777.json, inline-77777.json | 430 records, 3416 cases | 300 records, 1800 cases (12 renderings dropped) |

A standalone file holds 420 generated patterns x 8 subjects (4 random,
4 built from the pattern), 6 poke patterns x 8 subjects, and 4
nesting-depth patterns (40, 400, 3000, 60000) x 2 subjects. An inline
file holds 300 functions of one or two `match` arms each, x 6
single-value subjects (3 random, 3 built from an arm). A rendering is
dropped when an arm's matcher dialect source does not lower to the
tables of its spec; the generator then draws another function.

## Standalone files

`records`: `{id, spec, cases: [{subject, master}]}`. The spec is the
JSON form `oracle.build_pattern` reads (its table is in oracle.py); the
pattern is built with `Pattern.build` and run against each subject with
`oracle.EXTERNS`.

## Inline files

`records`: `{id, arms, names, owners, source, cases: [{subject,
master}]}`. `source` defines `case_fn`: it binds each slot name of every
arm to `"UNB"`, runs `(match data [[ARM1] "arm1"] [[ARM2] "arm2"] [else:
"miss"])`, and returns the arm label with each name's value (`"EMPTY"`
when reading the name raises). `arms` are the arm specs the source
writes in the matcher dialect, `names` the slot names in order, and
`owners` the arm that names each slot.

## Values and outcomes

A value is JSON data: int, str, bool and null as themselves; otherwise a
one-key object, `tuple`, `list`, `pair` (with `tail` when improper; an
empty `pair` with no `tail` is nil), `symbol`, `keyword`, `datum` (with
`position` and `binding` when set), `frame` and `dict` (sorted `[key,
value]` lists), `Pt`, `Box`, `poke`, `nest`, or `repr`.

An outcome is `{"hit": captures}`, `{"miss": true}`, `{"refused": type,
"message": ...}` (the build or the arm's compile raised), `{"raised":
type, "message": ...}` (the match raised), or, for an inline case,
`{"result": value}`. Exception types are compared; messages are not.

OUTDIR must be an absolute path: `run-master.sh` runs the generator from
the master build's directory.
