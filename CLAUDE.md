# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

**All Python execution must go through tox — never invoke `python`, `python3`, or `pytest` directly.**

```bash
# Build native C extensions (required before running tests)
make build-ext

# Run full test suite (phases in order)
make test
tox -qe test

# Run a specific test file or directory
tox -qe py -- tests/lib/test_pair.py
tox -qe py -- tests/compile/specials/

# Run tests with native debugger output
tox -qe gdb -- tests/<path>

# Lint (flake8)
make lint

# Type check (mypy)
make typecheck

# Build docs (Sphinx)
make docs

# Run the full tox suite (flake8 + tests)
make tox

# Regenerate opcode handler dispatch table (needed after editing opcodes.incl)
make handlers
```

## Architecture

Koskari is a LISP dialect for Python. It has three major layers that must be built in order: the C extension, then the Python compiler, then the bootstrap `.ki` sources that are compiled at load time.

### C Extension (`koskari/lib/`)

The native extension is the runtime foundation. It provides:

- **Types**: `atom.c/h` (symbol, keyword — interned), `pair.c/h` (cons cells + nil), `values.c/h` (multi-value return), `defer.c/h` (coroutine deferral), `namespace.c/h` (lexical scopes), `ref.c/h` (reference cells), `formals.c/h` (function parameter handling).
- **Bytecode**: Opcodes are defined in `opcodes.incl` using the `OP(name, style)` macro, which is included multiple times to generate both the enum and dispatch tables. Handler dispatch is in `handlers.incl` (auto-generated by `tox -e handlers` from `tools/opimpl.py`). Per-opcode implementations live in `koskari/lib/opcode/`.
- **Evaluator** (`eval.c`): Custom stackless bytecode evaluator. Supports coroutines, delimited multi-shot continuations (prompt/shift and call/cc), dynamic wind/unwind, and ambiently async execution (awaitable results are automatically awaited in-place). Entry point: `koskari_eval(ctx, out_ev, send_val, throw_typ, throw_exc)`.
- **DynChain** (`dynchain.c/h`, `dynchain/`): Event-driven dynamic extent node chain tracking `with`, `try`, dynamic wind, parameterize, and continuation boundaries.

### Python Compiler Layer

- **Reader** (`koskari/reader/`): Parses s-expressions. `parser.py` contains `Reader`, `SourceStream` (wraps a C `BaseSourceStream`), and `LayoutReader` which converts indentation-based layout blocks into s-expression forms. Layout handlers for `if`, `cond`, `try`, `class`, etc. live in `koskari/reader/layouts/`.
- **Compiler** (`koskari/compile/`): `compiler.py` converts source forms into bytecode `Code` objects. Special form handlers are in `compile/specials/` (one file per form family: `lambda_.py`, `let.py`, `conditionals.py`, `continuations.py`, etc.). Compile-time pragmas are in `compile/pragma/`.
- **Lexer** (`koskari/lexer/`): Token stream used by the REPL and LSP. The prompt_toolkit REPL integration is in `koskari/lexer/prompt_toolkit/`.
- **Serializer** (`koskari/serialize/`): Codex format for persisting compiled `Code` objects (`.kio` files).

### Bootstrap and Module System

- `koskari/bootstrap/*.ki` — Core builtins written in Koskari itself (`basics.ki`, `_functions.ki`, `_conditionals.ki`, etc.). These are compiled and loaded at package import time by `koskari/bootstrap/__init__.py`.
- `koskari/__init__.py` installs the import hook via `koskari.importer`, which allows `import` of `.ki` source files and `.kio` compiled objects.
- `koskari_importer.py` / `koskari.pth` — Standalone hooks that activate when the package is installed.

### Testing

Tests run in 9 ordered phases via `tools/pyphase.py` (invoked by `tox -e test`):

| Phase | Marker | Coverage |
|---|---|---|
| 1 | `phase_lib` | C extension types, opcodes |
| 2 | `phase_infra` | matcher, reader, lexer, dis |
| 3 | `phase_compile` | compiler helpers, syntax, bytecode |
| 4 | `phase_specials` | special form compilation |
| 5 | `phase_importer` | import hooks |
| 6 | `phase_basics` | koskari-written builtins |
| 7 | `phase_cli` | CLI |
| 8 | `phase_reproducers` | full-stack regression scenarios |
| 9 | `phase_extras` | pygments, sphinx, lsp |

Native memory tests (C-level) require a container: `make test-native`, `make test-asan`, `make test-valgrind`.

### Corpus (`docs/corpus/records/`)

Language behavior test cases stored as multi-document YAML shards. Each record has `id`, `feature`, `source`, and `verify` fields (with expected results at `read`, `expand`, `compile`, and/or `eval` phases). Export to Parquet: `make corpus-parquet`.

### Documentation Boundaries

- `docs/` — user-facing Sphinx site. Never link or copy from `design/` here.
- `design/` — internal design docs, VM contracts, in-progress ideas. May link into `docs/`.

## Koskari Pair Idioms

These apply whenever working with `pair` objects in Python code:

```python
# Destructure a pair — do NOT use car()/cdr()
head, tail = body

# Build a list — cons is variadic, do NOT nest
lst = cons(1, 2, 3, nil)   # correct
lst = cons(1, cons(2, cons(3, nil)))  # wrong
```

## Python Style

- New `.py` files begin with the GPLv3 short-form comment block, then a blank line, then a module docstring with `:author:`, `:license:`, and `:ai-assistant:` fields.
- End every module with `# The end.` followed by a single newline.
- Two blank lines between all top-level definitions and between methods.
- Multi-line function signatures: double-indent continuation parameters (8 spaces); close paren on the last parameter line.
- Docstrings: triple double-quoted, opening/closing `"""` on their own lines, blank line between closing `"""` and first statement. End a line with a period only when another sentence follows in the same paragraph.
- Use `typing.Union` and related aliases; avoid the `X | Y` syntax (Python 3.10+) and `from __future__ import annotations`.
- `setup.cfg` is authoritative for package config, tox, flake8, and pytest settings. Do not add `pyproject.toml` content or Black config.

## C Style

- 2-space indentation; 79-character line limit.
- Files start with the GPLv3 block comment, then a `/** ... */` doc comment. End with `// The end.`.
- Multi-line function signatures: 4-space indent on continuation parameters.
- Negated pointer checks: `if (! ptr)` not `if (ptr == NULL)` or `if (!ptr)`.
- Section separators: `/* === Section name === */` with two blank lines before and one after.

## Git

Do not push. Do not run `git restore`, `git reset`, `git revert`, `git checkout`, `git merge`, or create/delete branches — only the user performs those operations. `git add` and `git commit` only when explicitly requested.
